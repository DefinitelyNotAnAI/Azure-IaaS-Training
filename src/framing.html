The Azure platform model

Before we touch individual resources, it helps to understand where those resources land in a well-governed Azure estate. Microsoft organises environments using a hierarchy designed for enterprise scale:

  • Management groups — govern policy and role assignments across all child subscriptions from one place.
  • Subscriptions — the billing and isolation boundary for workloads; one subscription per workload environment is the landing-zone pattern.
  • Resource groups — the deployment and lifecycle unit for a workload; everything in a resource group lives or dies together.

Everything you deploy in today's labs lives inside a resource group, inside a subscription, governed by policies set at the management group level.

How it fits: Azure Landing Zones

The landing zone pattern separates platform concerns (networking hub, identity, governance, security tooling) from workload concerns (the VNets, VMs, and storage accounts you are about to build). In a well-managed enterprise deployment:

  • A central hub VNet carries shared services — firewall, DNS resolver, VPN/ExpressRoute gateway.
  • Each workload subscription gets a spoke VNet, peered back to the hub — isolated address space, routed through the hub firewall for egress.
  • Azure Policy enforces configuration standards at scale: allowed VM SKUs, required tags, mandatory diagnostic settings, and more — automatically, without per-resource configuration.
  • Microsoft Defender for Cloud provides a unified security posture score and alerts across the entire estate.
