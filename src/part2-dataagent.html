Part 2 — Data Agent

Build your own Fabric Data Agent grounded on your slot's data — the NL-to-KQL layer your Part 3 agent will call.

What is a Fabric Data Agent?

A Fabric Data Agent is a natural-language interface grounded on one or more data sources (Eventhouse, Lakehouse, etc.). When asked a question in plain language, it generates and runs a KQL or SQL query against the grounded data and returns an answer.

In Part 3 your Foundry agent will connect to your Data Agent using the Microsoft Fabric tool. The Foundry agent handles reasoning, correlation, and recommendations — the Data Agent handles data retrieval. Keeping them separate means you can improve data queries without touching the agent's reasoning logic.

In this challenge you will create your own Data Agent grounded on your slot's functions, test it, and optionally refine its instructions for better answers.

Must-do — Create your Data Agent

  1. In the Fabric workspace, click + New item and select Data Agent (or find it under the AI + BI section).
  2. Name your agent: workshop-agent-userXX (use your slot to distinguish it from other participants' agents).
  3. Click Add data source → Eventhouse → select workshop-eventhouse → workshop-db.
  4. In the Select items to include panel, add:
    • The Telemetry table
    • Your slot functions: SlotTelemetry_userXX, SlotTickets_userXX
    • If you completed them: SlotCorrelation_userXX, SlotBlindSpots_userXX
  5. Under Instructions, paste the starter instructions below — then customise them for your slot.
  6. Click Save.
Reference agent available: The workspace contains a pre-built agent called workshop-agent-reference. If you get stuck, open it and copy its settings as a starting point.

Starter agent instructions

Copy these instructions into your Data Agent's Instructions field, then replace userXX with your slot:

You are a data analysis agent for the Azure IaaS Hackathon.

You help a participant understand how system behaviour (telemetry) is driving customer experience (support tickets) for slot <>.

Always filter your queries to SlotId == '<>'. Do not return data from other slots.

You have access to:
- SlotTelemetry_<>(): per-operation metrics (latency, errors, throughput) from the participant's VM.
- SlotTickets_<>(): simulated support tickets raised by customers reacting to system behaviour.
- SlotCorrelation_<>(): pre-built view of time windows where latency spikes and ticket bursts co-occur.
- SlotBlindSpots_<>(): time windows where tickets spiked but no telemetry anomaly was recorded.

When asked about incidents, latency problems, or customer complaints, correlate Telemetry spikes with Ticket bursts.
When asked about root causes, look for IncidentId values that link anomalous Telemetry rows to Ticket rows.
Always include timestamps, affected services, and customer tenants in your answers when available.

Must-do — Test your agent

After saving, use the Test panel in your Data Agent to ask these questions. All answers should reference your slot's data only:

  1. "What was the average latency in the last hour?"
  2. "Were there any latency spikes in the last 2 hours?"
  3. "How many support tickets were raised in the last 2 hours?"
  4. "Did any latency spikes coincide with an increase in support tickets?"

If the agent answers all four correctly (data in the right ballpark, slot-filtered), mark this challenge complete.

What good looks like:
  • Question 1: returns an average latency value in milliseconds, e.g. "Average latency was 187ms"
  • Question 2: identifies one or more spike windows with timestamps and latency values
  • Question 3: returns a ticket count, e.g. "12 tickets raised"
  • Question 4: identifies at least one correlated window and mentions the affected service

Stretch — Improve your agent's instructions

The starter instructions are generic. Refine them based on what you've seen in your data:

  • Name the specific services your app uses (from the Service column in Telemetry) so the agent can refer to them by name.
  • Tell the agent the normal latency range for your system (from Challenge 1 baselines) so it can reason about what counts as a spike.
  • Tell the agent that IncidentId is the key to connecting a telemetry spike to the customer-facing tickets it caused.

After improving the instructions, re-run the four test questions. The answers should be more specific and confident.
