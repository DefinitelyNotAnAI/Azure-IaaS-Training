Module 2 — VNet Peering

Watch the instructor demonstrate spoke-to-hub VNet peering — a core Azure Landing Zone pattern.

🎓 Instructor Demo — This module is facilitator-led. The instructor will demonstrate peering live using peer-hub.ps1 and the Azure portal. You don't need to take any action — follow along to understand the concept.

What you'll observe

The instructor will create the peering that connects your spoke VNet (, ) to the hub VNet (hub-vnet, 10.0.0.0/16).

Once peering reaches Connected, your spoke can reach the Azure Bastion in the hub — useful for Module 3 VM access. Note that peering is not required for the hackathon app to function: the legacy support app emits telemetry and support signals outbound over HTTPS, which works independently of hub connectivity.

  • The facilitator runs peer-hub.ps1 to create the hub side of the peering for all spokes.
  • Each spoke's peering name will be (spoke side) and (hub side).
  • Peering status should reach Connected within a minute after both sides are created.

How it fits into enterprise Azure

VNet peering is the standard connectivity mechanism between spoke and hub in an Azure Landing Zone:

  • Non-transitive by default — traffic between two spokes doesn't traverse the hub unless routed through the hub firewall via UDRs.
  • Low latency, high throughput — peering traffic stays on the Microsoft backbone and doesn't traverse a VPN gateway.
  • Both sides required — Azure requires a peering resource on each VNet. In production the platform team owns the hub side; in this lab a narrow delegated role lets you create both sides from one form.
  • Use remote gateway — if the hub has a VPN or ExpressRoute gateway, spokes can use it for on-premises connectivity instead of deploying their own.

What the instructor demonstrates

  1. The facilitator navigates to hub-vnet in the Azure portal and shows the Peerings blade (currently empty or partial).
  2. The facilitator runs peer-hub.ps1 from the local machine. This script creates the hub-side peering for each spoke in the cohort. Watch the terminal output — one peering entry per participant slot.
  3. Each participant can open their own VNet blade → Peerings and observe the peering entry changing from Initiated to Connected.
  4. The facilitator demonstrates the portal Add peering form on a test slot, showing the two-sided nature of peering (spoke side + hub side created in one form).
Want to try it yourself? If you want hands-on practice after the demo, you can optionally delete your peering and recreate it manually — but this is not required to continue the hackathon.
