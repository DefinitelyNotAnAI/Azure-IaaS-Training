Part 2 — Correlation View

Save your correlation query as a reusable function — this becomes the semantic layer your Part 3 agent will call.

Why save as a function?

Your Part 3 Foundry agent will call your Fabric Data Agent to answer questions about system behaviour. The Data Agent can be grounded on named KQL functions rather than ad-hoc queries — this gives the agent a stable, well-named interface to the data and makes its answers more consistent.

In this challenge you will:

  1. Save your correlation join as a named KQL function in workshop-db.
  2. Verify it returns the expected correlated windows.
  3. (Stretch) Build a blind-spot detector — finds windows where tickets spiked but telemetry shows no anomaly.

Must-do — Save your correlation function

  1. Open workshop-db in the Fabric workspace.
  2. Run the .create-or-alter function command below to save your correlation query as a named function.
  3. Test it by calling SlotCorrelation_<>() — it should return the correlated windows from Challenge 2.
// Save your correlation query as a named function
// Run this in workshop-db

.create-or-alter function
    with (docstring = 'Correlated spike + ticket windows for <>')
    SlotCorrelation_<>() {
    let spikeThresholdMs = 500;
    let spikeWindows =
        SlotTelemetry_<>()
        | summarize AvgLatencyMs = avg(LatencyMs), ErrorTotal = sum(ErrorCount) by bin(Timestamp, 5m)
        | where AvgLatencyMs > spikeThresholdMs;
    let ticketBursts =
        SlotTickets_<>()
        | summarize TicketCount = count() by bin(Timestamp, 5m)
        | where TicketCount > 3;
    spikeWindows
    | join kind=inner (ticketBursts) on Timestamp
    | project Timestamp, AvgLatencyMs, ErrorTotal, TicketCount
    | order by Timestamp asc
}

Stretch — Blind-spot detector

A blind spot is a ticket burst with no corresponding telemetry anomaly. It means users are experiencing a problem that your monitoring didn't catch — a perception gap. Save this as another function:

// Blind-spot detector: ticket bursts with no telemetry anomaly
.create-or-alter function
    with (docstring = 'Blind-spot windows for <>: tickets with no telemetry anomaly')
    SlotBlindSpots_<>() {
    let ticketBursts =
        SlotTickets_<>()
        | summarize TicketCount = count() by bin(Timestamp, 5m)
        | where TicketCount > 2;
    let anomalyWindows =
        SlotTelemetry_<>()
        | where IsAnomaly == true
        | summarize AnomalyCount = count() by bin(Timestamp, 5m);
    ticketBursts
    | join kind=leftanti (anomalyWindows) on Timestamp
    | project Timestamp, TicketCount
    | order by Timestamp asc
}
// Test it
SlotBlindSpots_<>()
Expected result: You may see a few blind-spot windows early in the session — this is intentional. The chaos engine injects some "noise" tickets that don't correspond to real system failures, creating the perception gaps your agent will need to distinguish from real issues.

Stretch — Early-warning detector

The inverse of a blind spot: telemetry degradation before tickets appear. The system is struggling but users haven't noticed yet — or the support channel lags behind the incident.

// Early-warning: telemetry anomalies with no ticket burst yet
let anomalyWindows =
    SlotTelemetry_<>()
    | where IsAnomaly == true
    | summarize AnomalyCount = count(), AvgLatencyMs = avg(LatencyMs) by bin(Timestamp, 5m);
let ticketBursts =
    SlotTickets_<>()
    | summarize TicketCount = count() by bin(Timestamp, 5m)
    | where TicketCount > 2;
anomalyWindows
| join kind=leftanti (ticketBursts) on Timestamp
| project Timestamp, AnomalyCount, AvgLatencyMs
| order by Timestamp asc

Bridge to Part 3

You now have four named functions for your slot:

  • SlotTelemetry_<>() — all your telemetry, partitioned to your data
  • SlotTickets_<>() — all your support tickets
  • SlotCorrelation_<>() — correlated spike + ticket windows (root cause evidence)
  • SlotBlindSpots_<>() — ticket bursts with no matching anomaly (stretch)

In Challenge 4 you will ground your Fabric Data Agent on these functions. Your Part 3 Foundry agent will then query them in natural language to find the planted root cause.
